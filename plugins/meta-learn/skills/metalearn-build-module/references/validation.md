# 教学模块验收规则

## 一、知识地图忠实性

- 模块核心问题在开篇被转化为学习者能理解的任务。
- 地图中的知识单元、内部关系、常见误区、任务和决策规则均有对应位置。
- 模块没有超出地图的课程边界；额外内容确实是理解的必要前置。
- 与前后模块的依赖关系清楚，不提前使用尚未教授的理论结论。
- 任何删减、合并或改序均能说明教学理由。

## 二、知识与证据

- 关键时间节点不矛盾，同时关系不被单线叙事抹去。
- 空间表达区分相对方位、行政范围、主张范围、实际控制和经济人口区。
- 关键人物、事件和组织被放在过程中解释，不是孤立名词。
- 因果解释包含中间环节，不用一个人物、技术、地理或事件承担全部原因。
- 基本史实、推断、争议与教学简化有可辨认的语言边界。
- 重要主张有可追溯来源；来源直接支持页面中的表述。

## 三、教学有效性

- 学习者在首屏知道本模块要解决什么问题，不被概念目录开场。
- 每个新概念都有具体例子、定义、关系和反例或边界。
- 设计不假设学习者知道未在地图前置模块或当前模块中教过的知识。
- 识别、比较、解释和迁移之间有可见的难度递增，不直接跳到开放写作。
- 主动回忆分布在主要学习阶段，学习者先输出再看到提示；局部任务没有全部堆到模块结尾。
- 完成条件与题目要求一致，不把“文本框非空”当作有效输出。
- 反馈解释判断过程，不只暴露标准答案。
- 最终任务要求重建关系或分析新材料，不只复述朝代、人名和概念。

## 四、交互真实性

逐一列出控件并核对：

- 用户操作前看到什么？
- 操作后主图、关系、数据、分类或推理状态发生什么变化？
- 这个变化为什么比静态文字更有助于理解？
- 初始状态、全部切换状态、重复点击、返回与进度恢复是否一致？
- 按钮的 `aria-pressed` 或展开状态是否与视觉状态一致？
- 不看颜色、不用鼠标或小屏使用时，核心教学关系是否仍可理解？

只改变标题、注释或进度文字，但不改变主图或思考状态的控件，默认判定为无效交互。

## 五、技术与视觉

- HTML 能解析，内联脚本语法正确，标识唯一，页内链接和可访问性引用指向存在目标。
- 实际测试核心操作路径，不以代码中存在监听器代替交互验收。
- 小屏、长文字、明暗主题与减少动效按实际功能和现有设计体系验证。
- 图形文字可读，图示不依赖颜色作为唯一区分，点击目标和焦点状态清楚。
- 遵守 `impeccable` 选定的操作指南、工艺底线和最终检测，不用通用“卡片墙”代替对当前知识的表现设计。

## 六、子代理独立审查

- 内容与教学子代理已对照知识地图和成品完成审查。
- 界面与交互子代理已使用 `impeccable` 完成审查。
- 技术与可验证性子代理已审查脚本、状态和验证证据。
- 子代理获取的是原始材料和审查标准，没有被提前告知主代理的结论。
- 主代理已核实、取舍和修复子代理发现，并重新运行受影响的检查。
- 大幅修改后，相关专项子代理已完成定向复查。

## 七、交付证据

只报告实际完成的检查：

- 已运行的结构、语法、状态映射和设计检查。
- 已人工核对的地图覆盖项和证据边界。
- 三个专项子代理的主要发现、主代理判断和对应修改。
- 已通过浏览器或截图验证的页面和状态。
- 未能运行的检查及其原因。
