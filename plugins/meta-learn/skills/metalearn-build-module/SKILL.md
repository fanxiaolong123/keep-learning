# 依据知识地图构建交互教学模块

将知识地图中的一个模块转换为可独立学习的交互式 HTML。把本技能当作方向与质量门槛，不当作页面模板：知识地图决定“学什么”，教学与界面设计决定“怎么学”。

## 一、确认前提

1. 必须先定位知识地图文件。
   - 优先使用用户明确指定的文件。
   - 未指定路径时，在项目范围内用 `rg --files` 查找文件名含“知识地图”“学习地图”“学习计划”或 `Learn Plan` 的文件。
   - 只有一个明显候选时直接使用；多个候选会导致模块范围不同时，请用户指定。
2. 必须完整读取知识地图，包括 HTML 脚本中的数据对象，不得只读取页面标题。
3. 必须确认目标模块。结合地图状态、现有模块文件和用户请求推定；若仍存在会改变课程范围的歧义，再询问用户。
4. 没有可用知识地图时停止生成，说明缺少的文件；不得仅凭旧模块反推一份新地图。

## 二、确认课程执行方式与 Goal

完整读取知识地图后，先列出计划内模块、已完成模块、第一个未完成模块和剩余数量。用户已明确指定执行方式时不重复询问；否则在开始第一个模块前只确认一次：

- **连续执行到结束**：完成全部剩余模块，并在最后自动执行 `$metalearn-assemble-handbook`。只有用户明确选择此方式后，才能创建课程级 Goal。
- **每个模块确认后继续**：本次只完成一个模块，交付后等待用户确认；不创建 Goal，下次继续时重新加载本技能并重新读取知识地图。

### 连续模式的 Goal 规则

1. 确认当前环境提供 `get_goal`、`create_goal` 和 `update_goal`；缺少时明确说明无法保证自动续跑，让用户改选逐模块确认，不得假装已经创建 Goal。
2. 创建前先调用 `get_goal`：
   - 没有活动 Goal：创建课程级 Goal。
   - 已有与同一知识地图和课程目录匹配的活动 Goal：直接恢复，不重复创建。
   - 已有其他未完成 Goal：停止并请用户先处理该 Goal，不得覆盖。
3. 用户未明确给出 token 预算时，不传 `token_budget`。
4. 创建 Goal 时，把知识地图绝对路径、课程目录、第一个未完成模块和全部剩余模块写入以下目标；不得只写“完成课程”这类模糊目标：

```text
依据〈知识地图绝对路径〉，在〈课程目录〉中从〈第一个未完成模块〉开始，按知识地图顺序完成〈剩余模块清单〉，并最终组装成本地学习手册。

每次 Goal 自动续跑及每个模块开始时，先调用 get_goal，并重新加载当前可用的 $metalearn-build-module（插件环境中可能显示为 $meta-learn:metalearn-build-module），完整读取其当前 SKILL.md；再重新读取知识地图和本模块要求的参考文件，不依赖上一轮记忆代替加载。

一次只处理一个模块。每个模块必须完成调研、教学设计、实现、三项独立审查和最终验证；全部通过后才能更新知识地图状态并进入下一模块。不得跳过、调序、重复生成或覆盖无关用户修改。

全部模块完成后，重新加载 $metalearn-assemble-handbook（插件环境中可能显示为 $meta-learn:metalearn-assemble-handbook），完成统一入口、连续导航、本地启动器和最终验收。

只有知识地图、全部计划内模块和学习手册都通过各自要求的验证，Goal 才算完成。
```

5. 每次自动续跑开始都重新调用 `get_goal` 并完整读取本技能；知识地图是模块进度的唯一来源，Goal 不替代地图状态。
6. 一个模块验证通过后，才把对应地图状态更新为完成：
   - 仍有未完成模块：简洁报告进度，不询问是否继续，不调用 `update_goal`，让 Goal 自动进入下一个模块。
   - 已完成最后模块：直接重新加载并执行 `$metalearn-assemble-handbook`，不再请求一次重复确认。
7. 只有手册最终验收完成后才能把 Goal 标记为 `complete`。不得因预算将尽或暂时困难提前完成；只有同一阻塞连续出现三次 Goal 续跑且无法继续时，才按 Codex Goal 规则标记 `blocked`。

## 三、确保界面设计依赖

1. 在开始界面方向、编码或审查前，确认当前环境已有 `impeccable` 技能。
2. 若没有，先通过现有的技能发现或安装能力查找并安装 `impeccable`。安装需授权时请求用户批准；无法安装时停止界面生成，不得默认跳过。
3. 完整读取并执行 `impeccable` 的当前指令：只运行一次上下文检查，读取对应操作指南，编辑界面前读取工艺底线。
4. 将教学页视为“理解+操作”的混合界面，由具体任务决定阅读和操作的比重，不预设一种固定布局。

## 四、提取模块契约

从知识地图中提取并在工作中持续对照：

- 整体学习目标、学习者起点和课程边界。
- 目标模块的核心问题、前后依赖、知识单元与时空范围。
- 必须形成的概念区分、因果链、常见误区、迁移能力和决策规则。
- 地图给出的任务、可靠性标记、证据边界和资料线索。

建立一份内部“覆盖对照表”，把每个地图要求对应到：教学位置、解释方式、交互或练习、最终检查。这份表为质量工具，不得变成固定页面结构。

## 五、调研与建模

1. 根据目标模块单独调研，不把知识地图当作足以支撑所有史实的来源。
2. 优先使用原始材料、学术机构、博物馆、大学、政府或权威出版机构资料。精确主张、争议问题和可能更新的信息必须核实。
3. 区分基本史实、有依据的推断、学界争议和教学性简化。图示无法表达精确疆界、比例或因果强度时，必须明示。
4. 建立连续的时间、空间、人物与组织、事件、制度和因果关系，不用几个著名节点代替整体过程。
5. 只补足理解地图模块所必需的前置知识，不把模块扩张成一门通史或专门史。

## 六、设计教学路径

编辑前完整读取 [references/pedagogy.md](references/pedagogy.md)。

1. 从可观察的材料、具体场景、错误模型或真实问题进入，再逐步命名概念和抽象关系。
2. 给每个关键知识点补齐“是什么、为什么、如何与前后连接、哪些结论不能由此推出”。
3. 让任务按“识别→比较→解释→迁移”逐步提升，但不强制固定章节数量或实验站形式。
4. 把主动回忆分布在主要学习阶段：先要求学习者脱离正文做短输出，再开放提示或参考；不得把所有输出堆到模块末尾，也不得把直接展开参考答案算作主动回忆。
5. 根据知识关系选择表现形式。时间、空间、层级、网络、因果、证据和多视角应使用不同的表现逻辑。
6. 交互必须帮助理解一个关系或完成一次推理。装饰性点击、只更换旁边文字而不改变主图的“假交互”不得交付。
7. 给练习提供有信息的反馈，说明错在哪个判断环节，不只显示对错。完成判定必须对应题目要求，不能只检查文本框是否非空。

## 七、实现模块

1. 在已有课程中创建后续模块时，至少检查一个前置模块和一个现有视觉依据，保持学习连续性、术语一致性和必要的视觉连续性。
2. 不复制旧模块的章节骨架。允许根据当前知识关系重新组织导航、阅读节奏、图示和操作方式。
3. 遵循 `impeccable` 对当前项目和目标页面的指引。内容正确不是降低界面质量的理由，视觉吸引也不是删减知识解释的理由。
4. 优先交付可独立打开的 HTML，除非用户或现有项目明确要求其他技术形式。
5. 学习进度、主题、小屏适配和其他功能是按使用场景决定的能力，不是每个模块都必须复制的固定部件。
6. 保留现有文件中与本任务无关的用户修改。使用 `apply_patch` 编辑文件，并避免破坏性操作。

## 八、派出独立子代理审查

模块实现和主代理首轮自检完成后，必须派出三个不直接编辑文件的专项子代理；可并行时并行进行：

1. **内容与教学审查**：对照知识地图检查覆盖、史实、证据边界、知识连续性、解释充分性和难度递增。
2. **界面与交互审查**：必须使用 `impeccable`，检查信息层级、认知负担、表现形式、交互真实性、可访问性和小屏表现。
3. **技术与可验证性审查**：检查脚本、状态映射、进度恢复、标识和链接、浏览器验证证据；遇到安全策略阻止时，只提供静态替代证据，不绕过限制。

向子代理只提供知识地图、成品、相关来源和审查标准。不提供主代理的预期答案、已有结论或怀疑点，避免子代理只是重复主代理的判断。

要求每个子代理按“严重程度、准确位置、证据、影响、修改建议”输出发现。子代理不直接修改成品。

主代理必须：

- 汇总并用原始文件和知识地图核实每项发现，不机械接受子代理结论。
- 修复经证实的问题，并重新运行相关检查。
- 若修改改变了大段教学路径、核心交互或史实解释，让原专项子代理再做一次定向复查。
- 承担最终验收和交付责任；子代理审查不代替主代理判断。

当前环境不支持子代理时，不得把主代理自检宣称为等价的独立审查；说明缺失的验收环节，并在宣称完成前请用户决定如何处理。

## 九、完成主代理最终检查

交付前完整读取 [references/validation.md](references/validation.md)。

1. **地图忠实性**：覆盖对照表每一项均有去处；任何有意删减都有理由。
2. **知识与教学**：史实、时空、人物、事件和因果能够连接；概念有解释；证据边界清楚；不预设学习者已掌握未教内容。
3. **交互与界面**：每个控件都导致可验证的状态变化；初始、切换、恢复和完成状态一致；键盘、文字说明和小屏使用可行。
4. **技术结构**：运行 `node scripts/validate-interactive-html.mjs <HTML路径>`，再按当前实现补充状态映射检查。使用浏览器或截图工具验证关键状态；若受安全策略限制，使用静态替代证据并在交付中说明，不宣称已完成视觉验收。

完成所有编辑后，按 `impeccable` 要求运行最终检查；设计检测只在最终编辑后运行一次。修复本次变更引入的问题，不擅自扩大到无关的全页重构。

## 十、交付

简洁报告：

- 生成或修改的模块文件。
- 如何落实知识地图的核心问题和迁移目标。
- 实际完成的内容、交互和技术检查。
- 三个专项子代理的审查结果以及主代理的处理结果。
- 仍然存在的证据边界或未能完成的视觉验收。

交付前重新读取知识地图并核对计划内模块及执行方式：

- 逐模块确认模式：若仍有未生成模块，明确下一模块并等待用户确认；若所有模块均已完成，提示下一步加载 `$metalearn-assemble-handbook`，等待用户确认。
- 连续模式：若仍有未生成模块，按 Goal 自动进入下一模块；若所有模块均已完成，直接加载并执行 `$metalearn-assemble-handbook`，不重复询问。

## 停止条件

在以下情况停止并请求用户处理，不用自行假设绕过：

- 找不到知识地图，或多份地图导致课程范围冲突。
- 目标模块不明确，且不同选择会显著改变交付内容。
- `impeccable` 缺失且无法安装。
- 缺少必要的用户资产、权限或外部资料，且无安全的替代方案。
